## 2.2 JWT 관련 정보를 저장하는 In-Memory DB인 Redis 사용
JWT는 서버에서 임의로 무효화할 수 없다는 한계점이 존재합니다. 이를 보완하기 위해 Redis를 토큰 상태를 저장하는 DB로 활용하여, JWT인증방식의 Stateless의 장점을 유지하면서 동시에 토큰을 컨트롤 할 수 있습니다.
**설계 의도**
- JWT의 구조적 한계인 "발급 후 서버측에서 제어 불가"를 Redis의 TTL 기반 저장소로 보완했습니다.
- RDB 부하 없이 토큰 조회/검증을 빠른 속도로 처리할 수 있습니다.

<br>

**Redis 키 설계**
| 키 패턴 | 용도 | TTL |
|---------|------|-----|
| `access_token:{username}` | 현재 유효한 Access Token 저장 | 1시간 |
| `refresh_token:{username}` | 현재 유효한 Refresh Token 저장 | 12시간 |
| `blacklist:{token}` | 로그아웃된 토큰 무효화 | 1시간 |
<br>
<br>

**동작 시나리오**
<br>
로그인 성공: <br>
Redis SET access_token:john "example..." TTL 3600 → Redis SET refresh_token:john "example..." TTL 43200

매 요청마다: <br>
JwtAuthenticationFilter → 쿠키에서 JWT 추출 → Redis GET blacklist:{token} → 블랙리스트 여부 확인 → 블랙리스트 아닌 경우 → JWT 서명 검증 → 인증 처리

로그아웃: <br>
Redis SET blacklist:{token} "blacklisted" TTL 3600 → Redis DEL access_token:john, refresh_token:john

토큰 갱신: <br>
Redis GET refresh_token:john → 저장된 토큰과 요청 토큰 비교 → 불일치 시 → 재사용 공격으로 판단, 갱신 거부 → 일치 시 → 새 토큰 쌍 발급 + Redis 덮어쓰기
<br>
<br>
**기술적 특징**
- `StringRedisSerializer`로 키/값 직렬화 통일시켜 디버깅을 용이하게 했습니다.
- 사용자당 하나의 유효 토큰만 유지함으로써 다중 세션 제어를 가능하게 했습니다.

## 2.1 JWT를 통한 로그인 시스템과 Access/Refresh 이중 토큰 전략 사용

1. 세션을 사용하지 않는 Stateless 인증 아키텍처를 설계하고, Access Token과 Refresh Token을 분리하여 보안성을 챙겼습니다.
2. 확장시 서버의 메모리 문제를 감안하여 JWT 기반의 Stateless 구조를 채택했습니다.
3. Access Token의 짧은 만료(1시간)로 탈취 피해를 최소화하면서, Refresh Token(12시간)으로 재로그인 없는 UX를 유지하고자 했습니다.

**구현 핵심**

| 구분 | Access Token | Refresh Token |
|------|-------------|---------------|
| 만료 시간 | 1시간 | 12시간 |
| 저장 위치 | HttpOnly Cookie | HttpOnly Cookie |
| 갱신 방식 | Refresh Token으로 재발급 | **Token Rotation** (갱신 시 함께 재발급) |
<br>

**흐름도**: <br>
로그인 요청: <br>
AuthenticationManager 인증 → JwtTokenUtil: Access Token + Refresh Token 생성 → Redis에 양쪽 토큰 저장 (TTL 설정) → HttpOnly + SameSite=Lax Cookie로 클라이언트 전달
<br>
<br>
토큰 갱신 (POST /api/auth/refresh): <br>
Cookie에서 Refresh Token 추출 → type: "refresh" 클레임 검증 → Redis 저장값과 일치 여부 확인 (재사용/위조 방지) → 새로운 Access + Refresh Token 동시 발급 (Token Rotation) → Redis 갱신 + Cookie 재설정
<br>
<br>
로그아웃 (POST /api/auth/logout): <br>
Access Token → Redis 블랙리스트 등록 → 사용자 토큰 전체 삭제 (Redis) → Cookie maxAge=0 으로 삭제
<br>
<br>

**기술적 특징**
- `HttpOnly` 쿠키로 XSS를 통한 토큰 탈취 차단
- `SameSite=Lax` 설정으로 CSRF 공격 방어
- Refresh Token Rotation으로 토큰 재사용 공격 탐지
- Redis 블랙리스트로 로그아웃 후 토큰 즉시 무효화

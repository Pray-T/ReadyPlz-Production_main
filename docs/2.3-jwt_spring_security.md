## 2.3 JWT 특성에 맞춰 커스텀한 Spring Security 기반 인증/인가 처리
Spring Security의 기본 세션 기반 인증을 JWT구조에 맞게 커스텀하여, 필터 체인, 인증 흐름을 설계했습니다.

**설계 의도**
- Spring Security의 기본 폼 로그인/세션 메커니즘을 제거하고, JWT에 맞게 커스텀
- HTTP 요청과 WebSocket 연결 모두에서 동일한 JWT 인증 체계를 적용

**커스터마이징 구성 요소**
| 컴포넌트 | 역할 |
|----------|------|
| `SecurityConfig` | 세션 비활성화, JWT·CSRF 필터 등록, URL별 권한 설정 |
| `JwtAuthenticationFilter` | 매 HTTP 요청마다 JWT 추출 → 검증 → SecurityContext 설정 (`CsrfFilter`보다 앞) |
| `NonClearingCookieCsrfTokenRepository` | Cookie CSRF 저장소. JWT 인증 시 `saveToken(null)`로 `XSRF-TOKEN`이 지워지지 않게 함 |
| `CsrfCookieFilter` | Spring Security 6 deferred CSRF에서 GET에도 `XSRF-TOKEN` 쿠키가 내려가도록 토큰을 강제 로드 |
| `WebSocketAuthChannelInterceptor` | WebSocket CONNECT 시 JWT 인증 처리 |
| `CustomUserDetailsService` | DB의 Member + Role → Spring Security UserDetails 변환 |
| `JwtTokenUtil` | 토큰 생성, 파싱, 검증, 클레임 추출 담당 |

**SecurityConfig 핵심 설정** : <br>
SessionCreationPolicy.STATELESS:  <br>
세션 생성 완전 차단 (서버 HttpSession에 인증 상태를 두지 않음) <br><br>
CSRF: <br>
전역 비활성화가 아니라 Cookie CSRF 활성. 저장소는 `CookieCsrfTokenRepository.withHttpOnlyFalse()`를 감싼 `NonClearingCookieCsrfTokenRepository`. `/api/**`만 예외. Access Token을 HttpOnly 쿠키로도 전달하므로 SSR 폼·`/admin/**` 등 쿠키 기반 POST는 CSRF 토큰(`X-XSRF-TOKEN` 또는 폼 `_csrf`)이 필요합니다. 요청 핸들러는 XOR/SPA 핸들러가 아니라 `CsrfTokenRequestAttributeHandler`(`_csrf`)를 써 폼 hidden 값과 JS 쿠키 값을 같게 맞춥니다. 프론트 `apiClient.js`는 submit 시 폼 `_csrf`를 `XSRF-TOKEN` 쿠키와 동기화합니다. <br><br>
필터 배치: <br>
`JwtAuthenticationFilter`를 `CsrfFilter` **앞**에 둡니다. CSRF가 먼저 실패하면 JWT가 아직 없어 `AuthenticationEntryPoint`가 로그인 페이지로 리다이렉트하고, 닉네임 수정 등이 로그아웃처럼 보입니다. `CsrfCookieFilter`는 `BasicAuthenticationFilter` 뒤에 두어 deferred 토큰을 GET 응답 쿠키로 내보냅니다. <br><br>
인가: <br>
`/api/auth/**` → permitAll → 인증 없이 접근 가능 (로그인, 회원가입) <br>
`/admin/**` → hasRole("ADMIN") → 관리자 전용 경로 <br>
`/games/**`, `/messages/**`, `/members/profile/**` → authenticated → 로그인 필수 경로
<br>
<br>
**JwtAuthenticationFilter 처리 흐름** : <br>
요청 수신 → ① HttpOnly Cookie에서 accessToken 추출 (우선순위 1) → ② Authorization: Bearer 헤더에서 추출 (우선순위 2) → ③ Redis 블랙리스트 확인 → 무효화 토큰이면 차단 → ④ JWT 서명 + 만료 검증 → ⑤ UserDetailsService로 DB 사용자 조회 → ⑥ Redis 활성 access token(`access_token:{username}`)과 일치 여부 확인 → 불일치 시 차단(강제 로그아웃·다중 세션 제어) → ⑦ UsernamePasswordAuthenticationToken 생성 → ⑧ SecurityContextHolder에 인증 정보 설정 → 이후 Controller에서 Authentication 객체 사용 가능. 정적 리소스·`/health`는 필터를 건너뜁니다.
<br>
<br>
**기술적 특징**
- `OncePerRequestFilter` 사용으로 JWT에 맞게 요청당 1회만 실행 보장
- Cookie → Header 우선순위 기반 토큰 추출 (SSR + API 동시 지원)
- 인증 실패 시 `/api` 경로는 401 JSON 응답, 페이지 경로는 로그인 폼으로 리다이렉트
- `@PreAuthorize("hasRole('ADMIN')")` 메서드 레벨 보안으로 관리자 전용 경로 이중 방어
- JWT `STATELESS`와 Cookie CSRF를 같이 쓸 때 CSRF 쿠키가 매 요청마다 삭제되지 않도록 저장소를 커스텀
